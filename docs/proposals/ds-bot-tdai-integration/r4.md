## 1. 阶段一范围

**做：**

1. 会话归属解析（普通 / Bot 直聊 / Bot 分段 / 群成员 / 无法解析）。
2. 写入策略：Bot 相关会话**只写真人消息**，且必须有真人参与的轮才写。
3. 读侧与工具统一身份：Bot 会话读 canonical（= 现有 agent），工具不再走静态身份。
4. 失败策略：解析不确定时**停写并告警**，不回落、不猜测。

**不做（阶段二再议，见 §8）：** 为 Bot 建 agent、scoped viewAgent、关系型记忆、群聊记忆、Skill 自动沉淀、Loadout 借入、历史重放、canonical 摘要资产。

## 2. 身份解析

### 2.1 数据来源与路径

ds-bot home 解析顺序（与 ds-bot 一致）：

```
home = config.home（若插件侧无法读到 ds-bot 配置，则跳过）
     ?? join(DSH_HOME?.trim() || ~/.dsh, 'bot')
statePath = join(home, 'state.json')
```

- 进程启动与每次 pre-step 都重读（文件小，5 KB 量级）；带 5 秒级 mtime 缓存即可。
- 只读，**绝不写**这个文件或它同目录的任何文件。

### 2.2 索引：四个集合，缺一不可

【代码】ds-bot `src/host/store.js:333-352` 自己维护四张表，插件必须复刻同一套：

| 集合 | 来源 | 归属 |
| --- | --- | --- |
| Bot 当前会话 | `bots[*].sessionId ?? 键名` | botId |
| Bot 历史分段 | `bots[*].segments[*].sessionId` | botId |
| 群成员隐藏会话 | `rooms[*].sessions[botId]` | botId + roomId |
| 群成员历史分段 | `rooms[*].segments[botId][*].sessionId` | botId + roomId |

补充信号（不依赖 state.json 可读性）：

- `source.kind === 'bot'` 的消息（kickoff `[Bot team setup]`、`form:'relay'`、room 投递）——只要本会话出现过，就说明是 ds-bot 的会话。
- 会话 cwd 位于 `<ds-bot home>/workspace` 之下（团队默认工作目录）。⚠️ Bot 可自设 `workDir`，该信号**只作辅助**，不能单独定论。

### 2.3 四态判定（顺序执行，先命中先返回）

| 态 | 判定 | 行为 |
| --- | --- | --- |
| `bot-resolved` | sessionId ∈ 四集合索引 | 身份 = canonical；Bot 会话写入策略（§3） |
| `dsbot-unresolved` | 索引未命中，但会话内出现过 `kind='bot'` 消息 | **隔离**：不写 L0、不发 skill 沉淀；打告警（`sessionId` + 命中的 source.role） |
| `roster-degraded` | `state.json` 缺失/不可读/解析失败/`version` 非 1，且会话 cwd 命中 bot workspace，或本进程曾见过任何 ds-bot 信号 | **隔离**：同上，告警点名文件与解析错误原文 |
| `ordinary` | 以上都不命中 | 完全维持今天的行为（静态身份、全量回流） |

设计要点：**「是 ds-bot 的会话」由会话证据判断，「是哪个 Bot」才依赖 state.json。** 这样 roster 坏掉时不会把 Bot 会话当成普通会话。

懒保存窗口：Bot 刚建、`state.json` 尚未落盘时，会话会先落 `dsbot-unresolved`（隔离）而不是 `ordinary`——这是有意的，代价是新建 Bot 的头几轮不沉淀，不是污染主画像。

## 3. 写入策略

### 3.1 单一事实源

阶段一只写一个目标：**canonical agent（= 现有 `TDAI_MEMORY_AGENT_ID`）**。没有任何一条消息写第二个 agent。

### 3.2 分流表（capture）

| 条目 | Bot 会话 | 普通会话 |
| --- | --- | --- |
| `role=user` 且 `kind` 缺省/`'user'`/`'user-question-reply'` | **写入** | 写入 |
| `role=assistant`（含同 step 工具调用/结果） | **丢弃** | 维持现状 |
| `role=user` 且 `kind` 为其它（宿主注入、`'bot'` relay、skill-catalog、runtime-context） | 丢弃 | 丢弃 |

- 轮级门控：一轮里没有任何「写入」条目则整轮不写（纯 relay、定时触发、kickoff 轮天然不写）。
- 阶段一**不写**任何 Bot 产出，因此不引入 `[ctx bot:…]` 上下文封装。已知代价：真人那句「但我看好它的成长性」缺少上文，canonical 可能推成「用户偏好成长股」——这是阶段二（关系记忆）要解决的问题，见 §8。
- 群聊成员会话（`bot-resolved` + `roomId`）在阶段一**只写真人行**（若插件能从 `rooms[*].log` 的 `who/seq` 对齐出真人发言）；对不齐就整轮不写。阶段一不承诺群聊记忆。

### 3.3 写入契约

- 端点：`/v3/conversation/add`，字段仅 `session_id` + `messages[{role, content, timestamp?}]`。
- `content ≤ 8192`：超长真人消息按字符切分或截断（记一条台账）；单批 ≤ 100 条。
- 身份四元组沿用现有 `identityFor` 的四元组，仅 `agent_id` 在 Bot 会话下换成 canonical。

## 4. 读侧与工具

### 4.1 canonical 定义（消除歧义）

```
canonicalAgentId := cfg.agentId（TDAI_MEMORY_AGENT_ID，现有值，不新建、不改名）
```

- 阶段一**不调用**任何 agent 创建/更新接口；`AgentEntity.prompt` 保持现状（现有 agent 的 role/rules 注入不受影响，普通会话 prompt 不变）。
- 因此 R2-A1「shared Bot 与普通会话读到同一份人物约束」自动成立：两边 agent_id 相同。

### 4.2 读侧

| 会话态 | L3/L2 注入 | L1 召回 | 云端 skill 召回 / 知识 |
| --- | --- | --- | --- |
| `ordinary` | 现状 | 现状 | 现状 |
| `bot-resolved` | 现状（canonical） | 现状，query 见 §5.1 | 现状 |
| `dsbot-unresolved` / `roster-degraded` | **只读保留**（不因故障断掉上下文） | 同左 | 同左 |

### 4.3 工具身份（必须一起改）

`lib/tools.mjs:101`、`lib/tools.mjs:343`、`lib/recall.mjs:319`、`lib/assets.mjs:206` 都直接取 `cfg.agentId`。阶段一要求：**工具与注入取同一个解析结果**。

- 做法：`identityFor(session)` 改为返回解析后的身份（Bot 会话 → canonical），并对 `dsbot-unresolved` / `roster-degraded` 返回 `undefined`，让工具给出「本会话记忆未启用」而不是错误数据。
- 若某处改动风险高，可先给 `bot-resolved` 放行、其余保持现状，但必须与注入一致，不允许两套身份并存。

### 4.4 可读性开关

新增插件侧策略文件（插件自己的数据目录，不碰 ds-bot 的文件）：

```json
{ "version": 1, "bots": { "<botId>": { "memory": "shared" | "none" } } }
```

- 默认 `shared`；`none` 表示该 Bot 不注入、不写、工具也拒绝（用于试验型 Bot）。
- 文件缺失/解析失败 → 全部按默认 `shared`，并告警。

## 5. 查询、挂载与失败

### 5.1 召回 query 与挂载（单一规则）

- query = **本会话最近一条真人消息**的文本（判 `role` + `source.kind`，复用 `humanUserTexts` 的口径）。
- 本轮没有真人消息 → **不发 L1 请求、不插召回块**，只用 L3/L2。
- 去重：按 `(sessionId, 最后一条真人消息的 recordKey)` 记忆，**同一轮只插一次**（`agent/pre-step` 每 step 都会跑，多 step 长回答会重复注入）。
- 挂载点：插在最后一条真人消息之后；找不到则不插（去掉 `messages.length` 兜底）。

### 5.2 失败矩阵

| 情况 | 读侧 | 写侧 |
| --- | --- | --- |
| `state.json` 不存在（用户没用过 ds-bot） | 正常 | 正常（该场景下不会有 Bot 会话） |
| `state.json` 不可读 / 坏 JSON / `version` 未知 | 正常（canonical） | 命中 ds-bot 信号的会话**隔离**，其余正常 |
| 会话是 ds-bot 的但解析不出归属 | 正常（canonical） | 隔离 + 告警 |
| 插件策略文件坏 | 正常（默认 shared） | 正常 |

一句话：**读侧 fail-open，写侧 fail-closed。**

### 5.3 开关与回滚（两个，不是一个）

| 开关 | 默认 | 关掉后 |
| --- | --- | --- |
| `dsbotAwarenessEnabled` | 开 | 全部会话走 `ordinary` 路径 = 今天的行为 |
| `botSessionWriteMode`（`human-only` \| `off`） | `human-only` | `off` 时 Bot 会话完全不写，读侧不变 |

## 8. 明确延后（阶段二起，每条都要先出设计）

| 项 | 为什么延后 |
| --- | --- |
| scoped viewAgent / 角色化投影 | 需要先解决「同一真人消息不得双写」和「Core 无法产出关系型记忆」两个问题；当前 view L3 只会得到域内人物偏好，不是角色观察 |
| 关系记忆（「用户会反驳该框架」） | Core 的 L3 提示词不可改；需要插件侧自管的关系记录载体，属新设计 |
| 群聊记忆 | 群成员会话里真人发言与 Bot 转写混在一条 `kind='bot'` 消息内，需要按 `rooms[*].log` 对齐；阶段一先不写 |
| Skill 自动沉淀 | 依赖 Bot 产出进入会话记录；与「只写真人」冲突，需要独立的 skill-only 通道 |
| Loadout / 资产借入 | 接口存在但映射规则是独立设计 |
| 历史重放 | 会重新引入 Bot 产出，须先定过滤规则 |
| canonical 摘要资产 | 当前只能整篇读 L3（本机 21 KB 量级），摘要需要新资产类型 |
