## 4. 三处真正的分歧（决定胜负的地方）

### 分歧 1 · 身份怎么落地（b 对，a 错）

- **a**：`agent_id = "dsbot-" + bot.id`，靠派生保证稳定。[代码] `agentCreateSchema` 无 `agent_id`，此路不通。
- **b**：建 agent 时**接收服务端返回的 id** 并持久化；改名、改角色、换模型都不动映射；删除只停用、不复用 id。

这不只是 API 细节。a 的整个「单向派生、不建手工登记表、避免漂移」的论证，建立在一个不存在的接口能力上。**a 需要把这个论证整体换成 b 的做法**，而这会连带影响它 §5 的第 4 步（身份路由生效）。

### 分歧 2 · 解析失败时怎么办（b 更安全）

- **a**：「都拿不到 → 用今天的单一身份，行为不变」（§4.2 第 3 层）。
  兼容性上很聪明，但代价是：**Bot 的内容会写进主 agent 的 L0/L1，进而污染主画像**。而这正是两个插件结合要避免的事。
- **b**：「未声明、映射/创建/校验失败时，普通会话走旧静态身份；**Bot/room 关闭读写并告警，绝不写默认 agent**」（§4 M3 末段）。

一个把失败当降级，一个把失败当停写。**在「记忆会被永久写进画像」这个场景里，停写比降级正确。**

### 分歧 3 · L0 里要不要留 Bot 的话（a 更平衡）

- **a**：门控「一轮写入 L0 的充要条件 = 该轮至少有一条 actor=human」；被放行轮里 bot 产出标 `bot:<id>` **只作上下文**。
- **b**：「L0 仅写 human 块，assistant 自动回答一律不写」。

b 更彻底，但也更伤：L1 抽取器读到的将是**只有人说话、没有回应**的孤立片段，事实抽取质量会下降。a 的「标注但保留」是更好的折中——它满足「不沉淀自动化行为」的意图，同时保住了抽取所需的上下文。

## 5. 结论

**design-a 更优（87 vs 83），但不能直接用；design-b 分数低，却有两个设计必须被吸收。**

具体地说：

**a 必须改的（否则方案不成立）**
1. §4.2 的 id 派生整段，换成「服务端返回 + 持久映射」，并把 §5 第 4 步的判定同步改掉。
2. 第 3 层回落，从「用 config 身份继续跑」改为「Bot 会话停写 + 告警」；普通会话仍回落，两者要分开。
3. §8 第 3 条（写 L0 的请求体字段集未知）应当升级为**第一步就要验证的前置项**——a 自己也写了「这是本方案最可能在第一步就被否掉的点」，但落地步骤里没体现。

**b 值得被吸收的（a 没有的）**
1. 不可变映射的生命周期：改名/改角色/换模型不动映射，删除只停用不复用。
2. 失败即停写、绝不写默认 agent。

**b 明显不如 a 的地方**
1. 十点覆盖的深度：M1–M3 三块压掉了七个点，验收部分只有四条要点，没有 a 那种 A1–A7 的可执行判定矩阵。
2. 架构图只画了一条失败路径，没有把「解析失败 / 本轮无人 / 写 L0 失败」三条分开。
3. 缺 a 那个洞察：召回块本身会被下一轮 `lastUserText` 取到，形成自我召回（a §8.5 标了【推断】，但这确实是真风险）。

**一句话**：a 是「想得更全、写得更细，但踩了一个接口事实错误 + 一个安全策略错误」；b 是「想得更稳，但铺得不够开」。把 b 的两条塞进 a，这套方案就基本可用了。

## 6. 揭盲

| 编号 | 模型 | 总分 |
| --- | --- | --- |
| design-a | `opencode-go/deepseek-v4.1-flash` | 87 |
| design-b | `openai-codex/gpt-5.6-terra` | 83 |

差距 4 分，在一份 100 分制的 rubric 上属于**接近**。真正的差距不在总分，在错误类型：

- **a 错在「假设了一个不存在的接口能力」**——这是典型的"写得太顺、没回去核对 schema"。
- **b 错在「铺得不够开」**——这是典型的"简洁优先、细节让位"。

对这份工作的性质（要落地成代码）来说，**接口事实错误的代价高于覆盖不足**——因为它会在第一步就炸。所以如果只能选一份直接开工，我会选 b 的骨架 + a 的血肉；但按"谁的方案更优"这个问法，a 的完整性仍然赢。
